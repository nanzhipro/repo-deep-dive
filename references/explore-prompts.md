# Parallel Research Prompt Templates

> Phase 3 (Parallel Deep Dive) 中,启动并行研究线程、子代理或独立会话的 prompt 模板与场景化示例。
>
> 这些模板按能力写,不依赖特定产品。若你的运行环境提供 `Explore` 一类只读研究子代理,直接复用;若没有,把同一模板分发到多个独立会话,或串行执行。

## 通用骨架(每次启动研究线程都应包含)

```text
我在系统学习 <仓库标识> (<路径>)。已经知道:<Phase 1 全局描述>。

请帮我深度调研 <具体子主题>,用 <中文/英文> 报告(<字数范围>,信息密度优先,带 path:line 引用)。

### 任务
1. <具体问题 1>
2. <具体问题 2>
3. <具体问题 3>

### 输出要求
- 用 <中文/英文> 回复
- 关键代码片段建议 ≤ 15 行,每段带 path:line
- 信息密度优先,不要客套话
- 不修改任何文件,纯阅读
- 报告里如果引用文件内容,务必标明 path:line

### 边界(不要做什么)
- 不修改文件
- 不假设外部知识(只依据仓库实际内容)
- 不输出"基于以上分析"这类元话术
- 报告总长不超过 <N> 字
```

**填空要点**:

- "已经知道"段帮研究线程 / 子代理跳过 Phase 1 重复工作,直奔细节
- "具体问题"列分点列,**每个问题要可独立回答**,不要嵌套
- 字数范围给硬上限,防止研究报告写得太长把你的 context 撑爆
- "边界"列出来比"请简洁"明确得多

## 场景模板 1:整体架构调研

```text
请深度调研 <仓库> 的整体架构与目录布局。

### 任务
1. 顶层目录骨架:每个目录的职责、它们之间的依赖关系
2. 跨目录的"contract"是什么?(通过文件路径引用?通过 API?通过 manifest?)
3. 有没有 "single source of truth + sync" 这种 pattern?在哪?
4. 是否有多种部署形态(SDK / CLI / API / Plugin)?它们共享什么?
5. 仓库的"5 个不变量"是什么?(整个 codebase 都遵守的约定)

### 输出要求
- 中文,1500-2500 字
- 至少一张 ASCII 架构图
- 每个目录的职责一句话写清
- 列 ≥ 5 个不变量
- 引用 path 用相对路径
```

## 场景模板 2:核心模块深度解析

```text
请深度调研 <模块名/路径> 的内部结构。

我对这个模块的初步理解:<1-2 句话写你已经知道什么>。

### 任务
1. **模块体量**:文件数 / 总行数 / 关键文件清单
2. **核心抽象**:列出这个模块里的关键类 / 函数 / 概念,每个一句话定义
3. **关键设计选择 + 反例**:它做了 X 选择,但为什么不选 Y?
4. **挑 1-2 个最有代表性的样本逐行解剖**(每行做什么)
5. **依赖**:它依赖什么,被什么依赖
6. **限制 / 边界**:这个模块明确不解决什么

### 输出要求
- 中文,2000-3500 字
- 至少一个完整 worked example(代码片段 ≤ 15 行 + 逐行注释)
- 包含 ✅/❌ 对比
- 引用 path:line
```

## 场景模板 3:工程脚手架调研

```text
请深度调研 <仓库> 的工程脚手架:scripts/ + hooks + CI 工作流。

我已经知道:<Phase 1 提到的 high-level>。

### 任务
1. **每个脚本的职责**:scripts/ 下每个文件做什么
2. **关键逻辑摘录**:挑 3-5 个最关键的脚本,摘 ≤ 15 行核心逻辑
3. **git hooks**:有什么 hook?如何安装?
4. **CI 工作流**:有什么 workflow?何时触发?check 什么?
5. **"无聊但关键"的工程决策**:哪些设计是为了"长期可维护"而做的?(比如 version_bump、self-install hook、dry-run mode、idempotent 操作)
6. **可复用清单**:这套脚手架的哪些 pattern 我可以抄到自家项目?

### 输出要求
- 中文,2000-3500 字
- 列每个脚本一张表(脚本 / 职责 / 关键代码位置)
- 复用清单用 checkbox 形式
```

## 场景模板 4:演进史与设计变迁

```text
请基于 git log 分析 <仓库> 的演进轨迹。

### 任务
1. **时间线**:从最早 commit 到现在,挑 10-15 个里程碑 commit(用 git log --oneline 看)
2. **早期 vs 现在**:仓库一开始解决什么问题?现在变了吗?
3. **设计变迁**:哪些核心抽象改过名?(rename / restructure 提示)
4. **高频迭代区 vs 冷冻区**:哪些目录最近 30 天有大量改动,哪些半年没动?
5. **试验性 vs 稳定**:有没有标记为 preview / experimental / WIP 的部分?
6. **演进式洞察**:这条轨迹告诉我"产品迭代节奏"的什么?

### 输出要求
- 中文,1500-2500 字
- 时间线表格(日期 / commit / 一句话总结)
- 至少 3 条 "演进给我们的启示"(可复用到自家项目)
- 用 git log / git show 命令引用具体 commit
```

## 场景模板 5:扩展生态与第三方贡献

```text
请深度调研 <仓库> 的扩展机制:partner-built / plugins / examples / contrib 等。

### 任务
1. **第三方贡献入口**:第三方怎么加自己的代码进来?需要哪些文件 / PR 流程?
2. **扩展契约**:扩展必须遵守什么规范?有 lint enforce 吗?
3. **现有扩展样本**:挑 1-2 个第三方扩展,看它和官方扩展有什么差异
4. **网络效应分析**:这套扩展机制给项目带来什么商业 / 社区价值?
5. **可复用 pattern**:第三方扩展机制的哪些设计我可以抄?

### 输出要求
- 中文,1500-2500 字
- 列扩展目录结构与官方对照表
- 指出 3-5 个工程契约
- 总结这套机制的"双边网络"价值
```

## 场景模板 6:Runtime concerns

```text
请调研 <仓库> 在 production 运行时的关注点:observability / error handling / state / cost / eval。

### 任务
1. **可观测性**:有 logging / tracing / metrics 吗?接 OTLP 吗?
2. **错误处理**:模块失败 / 重试 / fallback 怎么处理?有显式策略吗?
3. **状态管理**:跨 session / 跨 process 状态怎么持久化?(KV / DB / 内存)
4. **成本 / token 经济学**:有 cost 关注的设计选择吗?(缓存 / 路由 / 节流)
5. **质量评估**:有 eval / golden test / regression 测试吗?
6. **留白(给 production 用户)**:仓库故意不实现什么,留给用户补?

### 输出要求
- 中文,2000-3500 字
- 每个关注点一节
- 引用具体配置 key / 代码位置
- 末尾给"如果你要 production,必须补齐的清单"
```

## 场景模板 7:横向对比与定位

```text
请帮我做 <仓库> 与同类工具/框架的横向对比。

我关心的对比维度:<列你的关注点,如:架构形态、多 agent 深度、状态管理、可观测性、学习曲线、生产成熟度>。

候选对比对象:<列 3-5 个,如 LangGraph / OpenAI Assistants / AutoGen / CrewAI / ...>

### 任务
1. **维度对比表**:每个维度,每个工具一格,简明描述
2. **核心差异**:每个工具的"本质定位"用一句话总结
3. **适用场景树**:在什么场景选哪个?
4. **<仓库> 的甜蜜点**:它最适合什么场景,与最不适合什么场景

### 输出要求
- 中文,1500-2500 字
- 对比表用 markdown 表格
- 适用场景树用代码块表示
- 不要泛泛说"X 好 Y 不好",要场景化
```

## 启动多个并行研究线程的建议

- **一次启动 2-3 个并行**(多个子代理、多个独立会话,或你自己分轮执行都可以)
- **每个研究线程的任务边界要清晰不重叠**(让一个看架构,另一个看脚本,避免重复工作)
- **设定不同的输出语言/长度**(整体调研要全面,细节调研要精确)
- **大型仓库可以一轮 3 个 + 第二轮 2 个**(根据第一轮发现决定第二轮重点)

## Tips

- 用 `path:line` 引用代替"在 main.py 里"(精确)
- 让每个研究线程用同一种语言(全中文或全英文),避免 mix
- 字数上限设硬一点(2500 字 > 5000 字,你来得及消化)
- 不要让研究线程做"分析",让它做"挖矿"(摘原文 + 标位置,你来分析)
